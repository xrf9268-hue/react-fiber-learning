# M1｜为什么 React 需要 Fiber

## 结论

Fiber 出现，不是因为 React 只想把框架“再提速一点”，而是因为旧的同步渲染模型对渲染工作的控制力不够。React 需要一种新的内部架构，把渲染从“开始后基本要一路做完”的整体事务，变成**可中断、可恢复、可排序、可放弃，但最终仍能一致提交**的工作流程。这样它才能在复杂更新下兼顾两件事：一是让用户交互及时响应，二是避免把半成品 UI 暴露给用户。[证据 1][证据 2][证据 3]

## 这一章要回答什么

本章只回答一个问题：**React 为什么需要 Fiber。**

暂不展开：
- Fiber 节点字段
- current / workInProgress 的结构关系
- lanes 的编码方式
- scheduler 与 work loop 的源码追踪

这些会留到后续模块。

## 一、先看旧模型的根问题

理解 Fiber，不能从“Fiber 是什么数据结构”起步，而要先看它要解决什么问题。

React 官方在 React 18 的说明里，直接对比了旧的同步渲染模型：**一旦一次更新开始渲染，在结果真正显示到屏幕之前，几乎没有东西可以打断它。**[证据 1] 这意味着如果一次更新规模较大，主线程就可能被长时间占住，新的输入、点击、切换等交互不能及时得到响应。

所以旧模型的核心问题，不应被草率概括成“React 太慢”，而应更准确地说成：**React 对渲染过程的控制粒度不够细。**

当一整块渲染工作只能从头跑到尾时，会同时出现三类压力：

1. **响应性压力**：用户已经产生了新的交互，但当前渲染还没让出执行机会。
2. **优先级压力**：更紧急的更新，未必能先于不那么紧急的更新被处理。
3. **陈旧工作压力**：某些尚未完成的渲染，做到一半时其实已经过时，但旧模型不擅长优雅地放弃它们。[证据 1][证据 2]

## 二、React 真正需要的不是“更快”，而是更强的工作控制能力

如果只把问题理解为“性能不够好”，很容易把 Fiber 误读成一次普通性能优化。但 React 官方真正强调的，是另一套能力：

- 把渲染工作拆开，而不是一口气做到底
- 在中途暂停，稍后继续
- 让更紧急的更新先处理
- 发现旧工作已经过时后，直接丢弃
- 在后台准备下一版界面，同时不阻塞主线程
- 在最后时刻再统一提交一致结果

React 18 发布文把这一点说得很清楚：并发渲染的关键性质是 **rendering is interruptible**；React 可以开始一次渲染，在中途暂停，稍后继续，甚至直接放弃这次进行中的渲染。[证据 1]

React 16 发布文用更早期的术语也表达了同样的方向：React 团队当时把 async rendering 描述为一种**协作式安排渲染工作、并周期性把执行权让回浏览器**的策略，其直接收益是**避免阻塞主线程，让应用更有响应性**。[证据 4]

因此，Fiber 要解决的根问题可以概括为一句话：**React 需要把渲染工作变成自己可以调度的工作系统。**

## 三、Fiber 提供的，不是一个新公开功能，而是一层新的内部基础

React 18 发布文把 concurrent renderer 称为 **behind-the-scenes change that unlocks powerful new capabilities**。[证据 1] 这句话对 M1 很重要，因为它提醒我们：

- Fiber 首先是**内部协调架构**的变化；
- 它的意义，不在于单独暴露了某一个 API；
- 它的意义，在于 React 从此具备了更精细地安排渲染工作的能力。

从教学角度，可以把 Fiber 暂时理解为 React 新的工作组织方式。它让 React 首次具备了下面这组能力：

- **可中断**：渲染不必一次跑到头
- **可恢复**：暂停后可以稍后继续
- **可排序**：更紧急的事情可以先处理
- **可丢弃**：过时的渲染工作可以直接放弃
- **可后台准备**：先在后台准备下一版界面，再决定何时提交

这里先不展开这些能力在源码里是如何编码成 Fiber 节点、alternate 树、lanes 与 work loop 的。M1 只需要建立一个稳定认识：**Fiber 的价值，在于让 React 对“渲染这件事”第一次拥有了架构级控制力。**

## 四、最关键的安全约束：可中断的是 render，不是对外可见的最终提交

如果只记住“渲染可以中断”，仍然不够，因为这句话很容易被误解成“React 可以边算边把半成品 UI 一点点挂到页面上”。这正是 M1 最需要避免的误解之一。

React 18 发布文明确写道：即使 render 被打断，React 仍然保证 UI 看起来是一致的；为此，React 会**等整棵树评估完成后，再执行 DOM mutations**。[证据 1]

React 18 升级文在 Suspense 一节又给出了一次更具体的说明：如果某个组件在完全加入树之前就 suspend，React **不会把这个未完成的新树以不完整状态加到界面上，也不会先触发它的 effects**；相反，它会直接丢弃这棵新树，等待异步条件满足后再重试渲染。[证据 3]

这说明 Fiber 背后的架构目标并不是“把不完整 UI 尽快显示出来”，而是：

- **render 阶段允许反复准备、暂停、重做、放弃**
- **commit 阶段才负责把一致结果真正交给用户**

2018 年官方的《Update on Async Rendering》也从历史角度说明了这一点：在 async rendering 下，render phase 与 commit phase 之间可能出现延迟，而 rendering 甚至可能在完成前就被打断。[证据 5]

所以，理解 Fiber 的分水岭不在“异步”两个字，而在这句更准确的话：**Fiber 让 React 获得了带一致性约束的可中断渲染能力。**

## 五、为什么“优先级”和“丢弃陈旧工作”是核心，而不是附带细节

React 18 引入 transitions 时，官方把更新分成了 **urgent** 与 **non-urgent** 两类。[证据 2] 这不是 API 层面的偶然包装，而是对 Fiber 存在理由的直接展示。

官方给出的例子非常清楚：

- 输入、点击、按键这类更新需要立刻响应，否则用户会感觉“不对劲”；
- 某些结果区、筛选结果、页面切换内容，则可以稍后完成；
- 如果用户在等待过程中又输入了新的内容，React 可以打断先前的非紧急渲染，并直接丢弃已经过时的那部分工作，只保留最新结果。[证据 2]

这背后的重点不是“更快算完所有事情”，而是**先做对用户此刻最重要的事，并避免把资源浪费在已经过时的结果上**。

因此，如果只把 Fiber 讲成“为了性能”，会丢掉最关键的一层：它首先解决的是**响应顺序与工作取舍问题**。

## 六、为什么 React 18 最能帮助我们看懂 Fiber 的意义

Fiber 并不是 React 18 才出现的。时间线上，Fiber 在 React 16 时期已经落地；React 16 官方发布文也已经明确把“协作式调度渲染工作”“周期性让出浏览器执行权”“避免阻塞主线程、提升响应性”视为重要方向。[证据 4]

但 React 18 让这套内部架构的意义第一次变得特别容易被外界看见，原因有两个：

1. **官方术语更成熟了。**
   - React 18 更系统地解释了 interruptible rendering、background preparation、consistent UI、transitions、Suspense、streaming SSR 之间的关系。[证据 1][证据 3]

2. **用户侧能力更可感知了。**
   - `startTransition` 让“紧急更新 / 非紧急更新”的区分进入了公开 API；
   - Suspense 与 streaming SSR 更清楚地展示了“后台准备、保持一致、适时提交”的架构价值。[证据 1][证据 3]

所以更准确的说法是：

- **React 16 是 Fiber 落地的时间点**；
- **React 18 是 Fiber 价值最容易被公开文档看懂的时间点**。

## 七、这一章最容易出现的三种误解

### 误解 1：Fiber 的目标主要是让 React 更快

不准确。更准确的说法是：Fiber 的首要价值，是让 React 能更细粒度地安排渲染工作，在复杂更新中兼顾响应性、一致性与工作取舍。性能收益当然可能出现，但它不是 M1 的主论点。[证据 1][证据 4]

### 误解 2：Fiber 就等于 Concurrent React，或者等于 React 18

也不准确。Fiber 是底层架构基础；Concurrent Rendering 是建立在这套基础上的能力集合；React 18 则是这些能力开始以更公开方式被使用和解释的重要版本。[证据 1][证据 3][证据 4]

### 误解 3：既然 render 可以中断，那 DOM 就会边算边改

恰好相反。官方反复强调的是一致性约束：React 会推迟 DOM mutations，不把不完整的新树直接提交给用户；必要时甚至会直接丢弃未完成的新树并重试。[证据 1][证据 3]

## 八、一句话记住 Fiber 为什么存在

**Fiber 存在，是因为 React 需要一种内部架构，把渲染从“不可打断的一整块工作”变成“可调度、可中断、可恢复、可放弃，但最终仍能一致提交”的工作系统。**
