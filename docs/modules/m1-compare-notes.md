# M1｜对照笔记：旧的同步渲染模型 vs Fiber 带来的能力

## 一眼看懂版

| 对比维度 | 旧的同步渲染模型 | Fiber 支持的能力 |
| --- | --- | --- |
| 工作推进方式 | 一次更新开始后，往往要一路做完 | 渲染工作可以拆开推进 |
| 中途控制 | 基本不可打断 | 可以暂停、继续，必要时直接放弃 |
| 对高优先级交互的处理 | 容易被当前大更新拖住 | 可以让更紧急的交互先得到响应 |
| 对陈旧工作的处理 | 已经过时的进行中工作不容易优雅放弃 | 可以丢弃未完成的陈旧渲染工作 |
| 主线程占用 | 大更新时更容易长时间占住主线程 | 更容易在过程中让出执行机会，降低阻塞 |
| UI 一致性 | 依赖一次性做完整体更新 | render 可中断，但 commit 前仍保持一致性约束 |
| 对外可见结果 | 通常是“做完再看到” | 可以后台准备下一版界面，成熟后再统一提交 |
| 能力外显 | 更像单一路径的同步计算 | 成为并发渲染、transitions、Suspense 等能力的基础 |

## 适合正文引用的压缩结论

旧模型的问题，不只是“可能慢”，而是 **React 对渲染工作的控制粒度不够细**：一旦开始，往往很难根据用户输入、优先级变化或结果过时与否，及时调整正在进行的工作。

Fiber 带来的关键变化，也不只是“算得更快”，而是 **把渲染变成可调度的工作系统**：可以中断、恢复、排序、放弃，并在保持最终提交一致性的前提下，把更重要的事情先做好。

## 可改成图示的最小骨架

```text
旧的同步渲染模型
  开始更新
    ↓
  持续执行
    ↓
  期间难以打断
    ↓
  做完后再看到结果

Fiber 支持的工作模型
  开始更新
    ↓
  拆分并推进渲染工作
    ├─ 可暂停
    ├─ 可继续
    ├─ 可让更高优先级工作先走
    └─ 可丢弃已过时工作
    ↓
  整棵树评估完成
    ↓
  统一 commit，保持 UI 一致
```
